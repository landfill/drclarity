Cursor 의 가격표는 모델마다 네 칸을 따로 둡니다 — `Input`, `Cache write`, `Cache read`,
`Output`. 100만 토큰당 단가이고, 값이 칸마다 따로 매겨집니다. 그래서 요청 하나의 비용은
토큰 총량 하나로 나오지 않습니다.

<strong>요청 비용</strong>은 그 요청에서 일어난 모든 호출에 대해 다음 넷을 더한 값입니다.

- Cache Read × 캐시 읽기 단가
- Cache Write × 캐시 쓰기 단가
- Input × 입력 단가
- Output × 출력 단가

앞의 세 항목이 **입력을 겹치지 않게 나눈 조각**이라는 점이 중요합니다. Anthropic 문서는
`입력 전체 = 캐시 읽기 + 캐시 쓰기 + 새 입력` 로 정의합니다. 같은 토큰이 한 호출 안에서
두 항목에 동시에 잡히지 않습니다.

<strong>캐시 읽기는 새 입력보다 훨씬 쌉니다.</strong> 단가 차이가 이 글에서 가장 실용적인
숫자입니다. 다만 배수는 공급자마다 다르므로, 숫자를 대려면 어느 공급자인지부터 정해야
합니다. Anthropic 은 Claude 모델에 대해 이렇게 못 박아 두었습니다.

- **캐시 읽기 — 새 입력의 0.1배**
- **캐시 쓰기 — 새 입력의 1.25배** (5분 캐시 기준. 1시간 캐시는 2배)
- 출력은 별개이고 보통 입력보다 비쌉니다

이 배수는 Claude 기준입니다. 다른 공급자의 모델은 다른 배수를 쓰고, 캐시 항목을 아예
보고하지 않는 모델도 있습니다. 그런 모델에서는 해당 항이 합산에서 빠집니다.

읽어 보면 이렇습니다. 같은 10만 토큰이라도 **캐시에서 가져오면 새로 처리할 때의 10분의 1**
값입니다. 대신 처음 캐시에 올릴 때 1.25배를 한 번 냅니다. 그러니 같은 문맥을 두 번만
재사용해도 이미 이득입니다 — 캐시가 없었다면 두 번 다 1.0배씩 냈을 테니까요.

여기서 실무적인 결론이 나옵니다. **싸다는 것과 적다는 것은 다릅니다.** 위 화면의 `Cost`
열을 보세요. 기본값에서 캐시 읽기는 토큰의 95% 인데 비용에서는 절반 남짓입니다. 1/10
단가 덕분입니다. 그런데도 **여전히 가장 큰 항목**입니다. 양이 그만큼 많기 때문입니다.

Cursor 가격표는 모델마다 네 칸을 따로 두므로, 쓰는 모델의 값은 그때 확인하세요.

실제 청구액은 이 식만으로 나오지 않습니다. 플랜에 포함된 사용량, Auto 라우팅이 고른
모델, 서드파티 모델에 붙는 추가 요율 같은 규칙이 그 위에 얹힙니다. 이 식은 **대시보드의
항목을 읽는 방법**이지 청구서를 재현하는 계산기가 아닙니다.
