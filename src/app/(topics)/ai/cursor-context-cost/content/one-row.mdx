export const title = '왜 Cache Write 가 0 인가';

실제 Usage 자료의 한 행은 이랬습니다. `Cache Read 647,221` · **`Cache Write 0`** ·
`Input 20,520` · `Output 6,350`, 그리고 `Total 674,091`. 네 값을 더하면 정확히 Total 입니다 —
우연이 아니라 정의가 그렇습니다. Cursor SDK 문서가 `totalTokens` 를 이 네 항목의 합으로
정의합니다. 즉 이 칸은 <strong>한 번에 들어간 문맥의 크기가 아니라 청구 항목의 합</strong>입니다.

눈에 걸리는 것은 `Cache Write` 가 0 이라는 쪽입니다. 155.2K 짜리 문맥을 쓰는데 캐시에
올린 것이 하나도 없다니 이상해 보입니다.

가장 그럴듯한 설명은 **이 요청이 그 채팅의 첫 요청이 아니었다**는 것입니다. 캐시는 같은
대화의 다음 메시지로 이어지므로, 앞선 턴들이 이미 문맥을 캐시에 올려 뒀다면 이번 요청이
새로 올릴 것은 남지 않습니다. 새로 처리한 것은 방금 보낸 메시지와 도중에 생긴 도구
결과뿐이고, 그래서 `Input` 도 20,520 으로 작습니다.

다만 이것을 확정할 수는 없습니다. 어떤 모델·공급자는 캐시 쓰기를 **별도 항목으로 보고하지
않고**, 그러면 그 칸은 조건과 무관하게 0 입니다. 캐시가 언제 만들어지고 언제 적중하는지도
접두부가 같은지, 유효 시간이 남았는지, 최소 길이를 넘겼는지에 달려 있습니다. 이 행이
어느 쪽인지 가르려면 모델과 캐시 조건을 알아야 합니다.

**확실한 것은 둘입니다.** 재사용이 크게 일어났다는 것(`Cache Read` 가 96%), 그리고
`Total` 이 항목의 합이라는 것. 위 화면은 앞선 턴이 캐시를 채워 둔 쪽을 가정합니다.

위 화면의 <strong>내부 호출 수</strong>를 1 로 줄여 보세요. `Cache Read` 가 문맥 한 번치인
155.2K 로 떨어지고 `Cache Write` 는 0 그대로입니다. 늘릴수록 그만큼 쌓입니다 — 한 행의
96% 를 캐시 읽기가 차지하는 이유입니다.
